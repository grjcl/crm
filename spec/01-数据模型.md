# 01 · 数据模型（16 张表 · PostgreSQL 16 · Flyway 口径）

> 权威来源：`PRD_一期_v1.3.md` §12（表清单/索引/排序视图）、§6.1（合作商字段）、§8（资源方字段）、§9（发现与商机字段）、§10（跟进与计划）、§11.2（渠道字段）。
> 迁移口径：单个 Flyway 脚本 `V1__init.sql`，按依赖顺序一次建齐 16 表 + 9 索引 + 1 视图；后续变更另起 `V2__…`。
> 本文是**契约的落地解释**：凡超出 PRD §12.1 字段清单的列，一律在 §4「契约变更建议」里单列，并标注「建议纳入 V1」。

## 0. 全局约定

| 项 | 口径 | 来源 |
|---|---|---|
| 主键 | `id bigserial PRIMARY KEY` | PRD §12 引言 |
| 审计列 | `created_at / updated_at timestamptz NOT NULL DEFAULT now()`，`updated_at` 由触发器维护 | PRD §12 引言 |
| 时区 | 库与连接统一 `Asia/Shanghai`；所有时刻为 `timestamptz`；「日期」类字段用 `date` | 技术方案 §3 |
| 软删 | 仅 `org` / `follow` / `attachment` 带 `deleted_at`（PRD 明确要求软删的三张表） | PRD §6.4、§6.8、§10.6 |
| 枚举存法 | **英文码存库、中文值传输**的取舍见 §0.2；本期取「中文值直接存库 + 传输」，与 PRD §13.3 示例完全一致 | PRD §13.3 |
| 字符集 | UTF8；文本长度按 **字符数**（PostgreSQL `varchar(n)` 即字符数） | — |
| 外键 | 事实表之间建 FK；`audit_log` 不建 FK（保留已删对象痕迹） | 本文约定 |
| 触发器 | `trg_<table>_updated_at` 统一调用 `set_updated_at()` | PRD §12 引言 |
| 迁移顺序 | 见 §1，表之间按 FK 依赖排序，**不可打乱** | 本文约定 |

### 0.1 枚举字典归属（对应 06 疑点 25）

| 类别 | 承载方式 | 运营可改 | 接口出口 |
|---|---|---|---|
| 合作分级 `战略/重点/普通` | 代码枚举 + `CHECK` | 否 | `GET /meta/dicts.level` |
| 合作状态 `潜在/试单/合作中/暂停/流失` | 代码枚举 + `CHECK` | 否 | `dicts.orgStatus` |
| 合作类型 `TMC/商旅分销/企业客户/其他` | 代码枚举 + `CHECK` | 否 | `dicts.orgType` |
| 产品线 `协议价/包房/团体/机+酒` | 代码枚举（JSONB 数组存值） | 否 | `dicts.productLines` |
| 跟进方式 `电话/拜访/微信/邮件/系统` | 代码枚举 + `CHECK` | 否 | `dicts.followType` |
| 抓取频率 `每日 08:00/每周一 08:00/每月 1 日/手动` | 代码枚举 + `CHECK` | 否 | `dicts.frequency` |
| 资源方类型 / 合作模式 / 结算方式 / 准入状态 | 代码枚举 + `CHECK` | 否 | `dicts.supply*` |
| 商机阶段 0–4 / 输单原因 | 代码枚举（小整数 + 枚举） | 否 | `dicts.dealStage` / `dicts.lostReason` |
| **合作标签** | **字典表 `org_tag`** | **是** | `dicts.tags` |
| **发现来源** | **字典表 `lead_source`** | **是** | `dicts.leadSources` |

**默认结论（06 疑点 25）**：只有标签与来源是表驱动、运营可改；其余走代码枚举 + `CHECK`，`/meta/dicts` 由后端常量组装并缓存。理由：改枚举值会牵动前后端映射与历史数据展示，一期 10 人使用无运营改枚举的诉求。

### 0.2 枚举「存中文」的理由与代价

- 理由：PRD §13.3 的示例响应直接是 `"level": "战略"`、`"status": "合作中"`、`{ "type": "电话" }`；存中文可让接口层零映射，且一期无多语言需求。
- 代价：改文案即改数据；因此 `CHECK` 约束里同时锁定取值，任何新增必须走 Flyway 变更（可追溯）。
- 若后续要国际化：新增 `code` 列 + 映射字典，属二期事项，不在本期。

## 1. 迁移顺序（`V1__init.sql` 的语句顺序）

```
0. 函数 set_updated_at()                   -- 所有表共用
1. sys_user                                -- 无外键，被 org/lead/deal/follow/attachment/audit 引用
2. org_tag                                 -- 无外键，被 org_tag_rel 引用
3. lead_source                             -- 无外键，被 lead 引用
4. channel                                 -- 无外键，被 lead_pool 引用
5. org                                     -- FK → sys_user
6. org_invoice                             -- FK → org
7. org_supply                              -- FK → org
8. org_tag_rel                             -- FK → org, org_tag
9. contact                                 -- FK → org
10. attachment                             -- FK → org, sys_user
11. follow_plan                            -- FK → org, sys_user
12. follow                                 -- FK → org, contact, deal*（deal 后建，见下）
13. lead                                   -- FK → lead_source, sys_user, org
14. lead_pool                              -- FK → channel, org? (仅 claimed_by → sys_user)
15. deal                                   -- FK → org, sys_user
16. audit_log                              -- 无 FK
17. 触发器 × 表                             
18. 索引（9 条契约索引 + 若干辅助索引）
19. 视图 v_partner_list
20. 基础种子（3 标签 / 7 来源）—— 见 §5，也可拆到 V2__seed.sql
```

> 依赖陷阱：`follow.deal_id` 指向 `deal`，而 `deal` 在 `follow` 之后建。两种落地方式二选一，**建议 A**：
> - **A（建议）**：先建表再加 FK —— `follow` 建表时不写 `deal_id` 的 FK，第 15 步 deal 建完后 `ALTER TABLE follow ADD CONSTRAINT fk_follow_deal FOREIGN KEY (deal_id) REFERENCES deal(id);`
> - B：把 deal 提到 follow 之前建。B 更简单，但 PRD §12.1 的表序是 follow 在前；顺序不构成契约，若实现者愿意可整体按 B。**本文件 DDL 按 A 写**。

## 2. 逐表 DDL

> 每张表给出：建表语句 + 索引 + 触发器 + 关键注释 + 「入库校验点」。命名一律 snake_case；列注释写在 `--` 行尾。

### 2.1 `sys_user` 用户（DB-TBL-01，S0）

```sql
CREATE TABLE sys_user (
  id            bigserial PRIMARY KEY,
  name          varchar(30)  NOT NULL,                       -- 姓名，列表与时间轴展示
  phone         varchar(11)  NOT NULL,                       -- 登录手机号，^1[3-9]\d{9}$
  employee_no   varchar(20),                                 -- 工号，如 1002
  dept          varchar(40),                                 -- 部门，如 商旅分销部
  role          varchar(10)  NOT NULL DEFAULT 'SALES'
                CHECK (role IN ('SALES','ADMIN')),            -- 一期仅两个角色（PRD §1.3）
  status        varchar(10)  NOT NULL DEFAULT 'ACTIVE'
                CHECK (status IN ('ACTIVE','DISABLED')),      -- 停用即刻下线（PRD §5.2）
  password_hash varchar(72)  NOT NULL,                        -- BCrypt，60 位定长，留余量
  pwd_changed_at timestamptz,                                 -- 管理员重置密码时间，用于提示改密
  last_login_at timestamptz,
  created_at    timestamptz  NOT NULL DEFAULT now(),
  updated_at    timestamptz  NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uk_user_phone ON sys_user(phone);
CREATE UNIQUE INDEX uk_user_employee_no ON sys_user(employee_no) WHERE employee_no IS NOT NULL;
CREATE TRIGGER trg_sys_user_updated_at BEFORE UPDATE ON sys_user
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

- **无 `avatar` 列**：PRD §12.1 未定义，原型用姓名首字做头像。见 06 疑点 13（建议一期不做头像字段，前端取 `name` 首字）。
- 入库校验点：`phone` 格式在服务端做正则兜底（唯一索引兜不住格式）；`employee_no` 允许空但非空时唯一。
- 无软删：停用用 `status`，不删行（历史跟进/审计要能显示操作人）。

### 2.2 `org` 合作商（DB-TBL-02，S2）

```sql
CREATE TABLE org (
  id            bigserial PRIMARY KEY,
  name          varchar(100) NOT NULL,                       -- 企业全称，2–100 字（PRD §6.1）
  short_name    varchar(20),                                 -- 简称，默认取名称前 4 字（服务端填）
  credit_code   varchar(18),                                 -- 统一社会信用代码，正则见 PRD §6.1
  legal_person  varchar(30),                                 -- 法定代表人
  reg_capital   varchar(30),                                 -- 注册资本，自由文本「5000 万元」
  found_date    date,                                        -- 成立时间，精度到月：存当月 01 日
  industry      varchar(30),                                 -- 行业，自由文本
  city          varchar(20),
  address       varchar(120),                                -- 注册地址
  website       varchar(80),
  brief         varchar(200),                                -- 企业简介
  type          varchar(10)  NOT NULL DEFAULT '商旅分销'
                CHECK (type IN ('TMC','商旅分销','企业客户','其他')),   -- PRD §6.1 / 清单 3.2
  product_lines jsonb        NOT NULL DEFAULT '[]'::jsonb,    -- 多选：协议价/包房/团体/机+酒（清单 3.3）
  level         varchar(10)  NOT NULL DEFAULT '重点'
                CHECK (level IN ('战略','重点','普通')),      -- 分级（清单 3.1）
  status        varchar(10)  NOT NULL DEFAULT '潜在'
                CHECK (status IN ('潜在','试单','合作中','暂停','流失')), -- 状态（清单 3.4）
  owner_id      bigint       NOT NULL REFERENCES sys_user(id),-- 归属销售（清单 2.8）
  collaborator_ids bigint[]  NOT NULL DEFAULT '{}',           -- 协作人，多选用户（C-01 已采纳，2026-11-24）
  created_by    bigint       NOT NULL REFERENCES sys_user(id),
  created_at    timestamptz  NOT NULL DEFAULT now(),
  updated_at    timestamptz  NOT NULL DEFAULT now(),
  deleted_at    timestamptz                                   -- 软删；回收站 30 天（清单 2.10）
);
CREATE INDEX idx_org_owner      ON org(owner_id)       WHERE deleted_at IS NULL;  -- 契约索引 3
CREATE INDEX idx_org_type_city  ON org(type, city)     WHERE deleted_at IS NULL;  -- 契约索引 4
CREATE INDEX idx_org_name       ON org(name)           WHERE deleted_at IS NULL;  -- 搜索/排序辅助
CREATE UNIQUE INDEX uk_org_credit_code ON org(credit_code)
  WHERE credit_code IS NOT NULL AND deleted_at IS NULL;   -- 信用代码唯一（排除空与已删）
CREATE TRIGGER trg_org_updated_at BEFORE UPDATE ON org
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

- `credit_code` 唯一索引**不在** PRD §12.2 的 9 条契约索引里，是查重（清单 2.9）的强约束落地；列入 §4 契约变更建议，标「建议纳入」。
- `product_lines` 用 JSONB 而非 PG `text[]`：PRD §12.1 明确写 `product_lines jsonb`。
- `found_date` 精度到月：接口入参 `YYYY-MM`，入库拼 `-01`，出参回 `YYYY-MM`。

### 2.4 `org_supply` 资源方扩展（DB-TBL-04，S2）

```sql
CREATE TABLE org_supply (
  id             bigserial PRIMARY KEY,
  org_id         bigint      NOT NULL UNIQUE REFERENCES org(id) ON DELETE CASCADE,
  supplier_type  text[]      NOT NULL DEFAULT '{}',        -- 多选：酒店集团/单体酒店/TMC/批发商/同业
  cities         int,                                      -- 覆盖城市数
  hotels         int,                                      -- 合作酒店数
  room_type      varchar(60),                              -- 主要房型
  peak_guarantee varchar(60),                              -- 旺季保障
  coop_mode      text[]      NOT NULL DEFAULT '{}',        -- 多选：协议价/包房/代理/散拼
  coop_start     date,                                     -- 合作起始
  settle_type    varchar(10) CHECK (settle_type IN ('预付','月结')),
  credit_days    int         CHECK (credit_days IS NULL OR credit_days >= 0),
  settle_contact varchar(20),                              -- 结算联系人（PRD §6.1 / 清单 4.4）
  access_status  varchar(10) CHECK (access_status IN ('考察中','合作中','暂停','淘汰')),
  reject_reason  varchar(100),                             -- 淘汰原因
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_supply_credit CHECK (settle_type IS DISTINCT FROM '月结' OR credit_days IS NOT NULL),
  CONSTRAINT ck_supply_reject CHECK (access_status IS DISTINCT FROM '淘汰' OR reject_reason IS NOT NULL)
);
CREATE TRIGGER trg_org_supply_updated_at BEFORE UPDATE ON org_supply
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

- 两条条件必填（清单 4.4 / 4.5）用 `CHECK` + 服务端 1001 双保险：`CHECK` 防脏数据，服务端给字段级提示。
- 仅当 `org` 打了「供应」标签时才写这行；不打标签时该行即使存在也不展示（PRD §8）。

### 2.10 `lead_pool` 待确认池（DB-TBL-10，S5）

```sql
CREATE TABLE lead_pool (
```

- 电话缺失时的指纹规则见 04 `R-DEDUP-02`（用空串占位，仅靠名称去重）。

### 2.11 `deal` 商机（DB-TBL-11，S5）

```sql
CREATE TABLE deal (
  id               bigserial PRIMARY KEY,
  org_id           bigint        NOT NULL REFERENCES org(id),
  title            varchar(50)   NOT NULL,                  -- ≤50 字
  stage            smallint      NOT NULL DEFAULT 0 CHECK (stage BETWEEN 0 AND 4),  -- 0接洽 1试单 2报价 3签约 4赢单
  stage_updated_at timestamptz   NOT NULL DEFAULT now(),    -- 每次 stage 变更刷新（停留天数口径）
  expect_nights    int           CHECK (expect_nights IS NULL OR expect_nights >= 0),
  expect_gmv       numeric(14,2) CHECK (expect_gmv IS NULL OR expect_gmv >= 0),
  expect_close     date,                                    -- 预计成交日期，≥ 今天（创建时校验）
  owner_id         bigint        NOT NULL REFERENCES sys_user(id),
  note             varchar(500),                            -- 说明
  result           varchar(10)   CHECK (result IN ('赢单','输单')),   -- 阶段 4 时必填
  lost_reason      varchar(10)   CHECK (lost_reason IN ('价格','资源覆盖','关系','需求变更','暂无预算')),
  closed_at        timestamptz,
  created_at       timestamptz   NOT NULL DEFAULT now(),
  updated_at       timestamptz   NOT NULL DEFAULT now(),
  CONSTRAINT ck_deal_result CHECK (stage <> 4 OR result IS NOT NULL),
  CONSTRAINT ck_deal_lost   CHECK (result IS DISTINCT FROM '输单' OR lost_reason IS NOT NULL)
);
CREATE INDEX idx_deal_org_stage  ON deal(org_id, stage);    -- 契约索引 6
CREATE INDEX idx_deal_stage_time ON deal(stage, stage_updated_at); -- 契约索引 7
CREATE INDEX idx_deal_owner      ON deal(owner_id, stage);  -- 「我的商机」分组
CREATE TRIGGER trg_deal_updated_at BEFORE UPDATE ON deal
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

- 无软删：一期没有删除商机的接口；「输单」是状态不是删除。
- `ck_deal_result` 与 `ck_deal_lost` 是 PRD §9.6「阶段到 4 必须选结果、输单必须选原因」的库级兜底，服务端同样校验并给 1001。

## 4. 视图 `v_partner_list`（DB-VIEW-001）

```sql
CREATE VIEW v_partner_list AS
SELECT o.id, o.name, o.short_name, o.level, o.status, o.city, o.owner_id,
       p.plan_date, p.note AS plan_note
FROM org o
LEFT JOIN follow_plan p ON p.org_id = o.id
WHERE o.deleted_at IS NULL;
```

## 6. 软删、审计与时间口径（在 04 有可测规则，此处只列落点）

| 主题 | 落点 | 说明 |
|---|---|---|
| 软删 org | `org.deleted_at` | 关联商机/跟进保留且不可见，恢复后一并可见（PRD §18-7） |
| 软删 follow | `follow.deleted_at` + `delete_reason` | 时间轴保留占位行 |
| 软删 attachment | `attachment.deleted_at` | 不删 OSS 对象（保留 2 年后再清理，见 06 疑点/§18-4） |
| 审计 | `audit_log` | 写操作全量：org / follow / plan / deal / tag / channel / user / transfer |
| 乐观锁 | `follow_plan.version` | 每次成功保存 +1，客户端持版本号提交 |
| 24h 编辑 | `follow.created_at` | 服务端比较 `now() - created_at <= 24h` |
| 阶段停留 | `deal.stage_updated_at` | `停留天数 = current_date - stage_updated_at::date` |
| 相对时间 | 不落库 | 前端按 `plan_date` 与今天算「今天/明天/N 天后/逾期 N 天」 |
