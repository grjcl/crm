## 0. 全局约定（每条接口都隐含）

| 项 | 规则 | 来源 |
|---|---|---|
| 前缀 | `/api/v1`，JSON，UTF-8 | PRD §13.1 |
| 鉴权 | `Authorization: Bearer {accessToken}`；缺失/失效 → `1002` | PRD §13.1 |
| 权限 | 角色不足 → `1003` + HTTP 403；客户端统一 toast「没有权限执行该操作」 | PRD §4.3-7、§14 |
| 响应体 | `{ code, message, data }`；业务错误 `code != 0` 且 HTTP 仍可 200（本项目统一 HTTP 200 + code，见 §0.3） | PRD §13.1 |
| 分页 | 入参 `page`（默认 1，≥1）、`size`（默认 20，1–100）；出参 `{ list, total, page, size }` | PRD §13.1、§4.3-1 |

| 幂等 | 所有 `POST` 写操作接受 `Idempotency-Key`（UUID v4，客户端生成）；同 key 24h 内重复请求返回首次结果。`PUT/DELETE` 天然幂等，不要求 | PRD §13.1、技术方案 §6.2 |
| 审计 | 所有写操作落 `audit_log`（action 见 04 `R-AUDIT-01`） | PRD §15 |
| 校验失败 | 返回 `1001`，`data.errors` = `[{field, message}]`，客户端定位到第一个字段 | PRD §13.4 |
| 软删对象 | 已软删的 `org` 对读接口返回 `1001`「对象不存在或已删除」；写接口同 | 04 `R-SOFT-01` |

`A` = SALES + ADMIN 均可；`ADM` = 仅 ADMIN；`OWN` = 仅本人（作者/归属人）可操作，ADMIN 可代办。完整矩阵见 04 §3。

## 2. S0 · 登录与账号（接口 1–4）

### BE-API-001 · POST /auth/login 手机号 + 密码登录

| 项 | 内容 |
|---|---|
| 权限 | 匿名 |
| 幂等 | 接受 `Idempotency-Key`；同 key 重放返回同一组 token |
| 需求来源 | PRD §5.1；清单 1.2；原型 `#login` |

**入参**

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| phone | string | 是 | `^1[3-9]\d{9}$`，否则 1001「请输入正确的手机号」 |
| password | string | 是 | 6–20 位且同时含字母与数字，否则 1001「请输入密码」 |

**出参 `data`**

| 字段 | 类型 | 说明 |
|---|---|---|
| accessToken | string | JWT，2h |
| refreshToken | string | 30d |
| expiresIn | int | 7200 |
| user.id | long | |
| user.name | string | |
| user.role | string | SALES / ADMIN |
| user.employeeNo | string | 可为 null |
| user.dept | string | 可为 null |

**错误码**：1001；2001（手机号未开通）；2002（手机号或密码错误——**统一文案，不暴露账号是否存在**）；2003（错误 5 次锁定 15 分钟）；5000。

**副作用**：写 `sys_user.last_login_at`；审计 `LOGIN`；Redis `login:fail:{phone}` 成功即清空。

**边界**：`status=DISABLED` 的账号返回 2001（与「未开通」同码，避免探测）并记审计；refresh token 有效期内重开 App 走 002 而不是 001。

**验收**：AC-AUTH-01 手机号格式校验生效；AC-AUTH-02 密码错误文案统一；AC-AUTH-03 连续 5 次错误后锁定 15 分钟；AC-AUTH-04 停用账号无法登录。

**依赖**：BE-SEC-001/004/009。

### BE-API-002 · POST /auth/refresh 刷新 token

| 项 | 内容 |
|---|---|
| 权限 | 持有效 refreshToken（可过期 accessToken） |
| 幂等 | 天然幂等；同一 refreshToken 在 30 天内可多次换取（轮换策略见 06 疑点 B5） |
| 需求来源 | PRD §5.3；清单 1.4 |

**入参**：`{ refreshToken: string }`（必填，JWT，30d）。

**出参**：同 001 的 `accessToken / refreshToken / expiresIn`（user 可省）。

**错误码**：1002（refreshToken 无效/过期/已登出）；2001（账号已停用）。

**副作用**：无审计（避免刷爆）；停用账号的 refresh 直接 2001 并加入黑名单。

**验收**：AC-AUTH-05 access 过期后静默续期，用户无感；AC-AUTH-06 已退出登录的 refreshToken 立即失效。

**依赖**：BE-SEC-001/003。

### BE-API-003 · POST /auth/logout 退出登录

| 项 | 内容 |
|---|---|
| 权限 | 已登录 |
| 幂等 | 是（重复调用返回 0） |
| 需求来源 | PRD §5.3；清单 1.4；原型「我的 → 退出登录」 |

**入参**：无（token 里的 `jti` 即目标）。

**出参**：`data: null`。

**错误码**：1002。

**副作用**：把当前 access 的 `jti` 与 refresh 的 `jti` 写 Redis 黑名单（TTL 各自剩余期）；审计 `LOGOUT`。

**验收**：AC-AUTH-07 退出后用旧 token 请求返回 1002。

**依赖**：BE-SEC-003。

### BE-API-042 · GET /meta/version 版本检查

| 项 | 内容 |
|---|---|
| 权限 | 匿名（启动时调用，可能尚无 token） |
| 需求来源 | PRD §5.4、§11.5；清单 1.6 / 7.5 |

## 4. S2 · 合作商与计划读写（接口 5–10、15、16）

### BE-API-005 · GET /partners 合作商列表

| 项 | 内容 |
|---|---|
| 权限 | A（一期不隔离，SALES 可见全部） |
| 需求来源 | PRD §7.1–§7.3；清单 3.5；原型 `#partners` |

**入参（query）**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| tag | string | 否 | 标签名精确匹配，`全部` 或缺省不筛 |
| city | string | 否 | 城市精确匹配 |
| level | string | 否 | 战略/重点/普通 |
| status | string | 否 | 潜在/试单/合作中/暂停/流失 |

| q | string | 否 | 模糊匹配 `name` / `short_name`，不区分大小写；服务端 `ILIKE '%q%'`，q 去首尾空格后为空视为不筛 |
| owner | long | 否 | 归属销售 id（二期「我的合作商」用；一期接口先留，不接入 UI） |
| page | int | 否 | 默认 1 |
| size | int | 否 | 默认 20，最大 100 |

**出参 `data`**

```json
{ "total": 11, "page": 1, "size": 20, "list": [{
  "id": 1, "name": "中航商旅服务有限公司", "shortName": "中航商旅",
  "level": "战略", "status": "合作中", "city": "上海", "type": "TMC",
  "industry": "TMC / 商旅服务", "owner": {"id": 2, "name": "王磊"},
  "tags": ["分销"],
  "lastFollowAt": "2026-11-18",
  "plan": { "date": "2026-11-25", "note": "给 2027 年度框架续签报价", "overdueDays": -5, "daysFromToday": 5 }
}]}
```

### BE-API-032 · POST /deals/{id}/advance 推进阶段

| 项 | 内容 |
|---|---|
| 权限 | A（负责人；ADMIN 任意） |
| 幂等 | 接受 Idempotency-Key（防双击推进两格——虽然只能一格，双击会连推两次） |
| 需求来源 | PRD §9.6、§9.8；清单 5.6；06 疑点 19 |

**入参**：path `id`；body `{ version?: int }`（可选乐观锁，见边界 3）。

**出参**：`{ id, stage, stageLabel, stageUpdatedAt, needResult: boolean }`。

**错误码**：
- 1001：`stage=4` 已结案（message「该商机已结案」）；
- 1003：非负责人且非 ADMIN。

**副作用**：
1. `stage = stage + 1`，`stage_updated_at = now()`；
2. 追加系统跟进 `follow{type:'系统', content:'商机「{title}」阶段由 {旧} 推进到 {新}', created_by:操作人, org_id}`（PRD §10.4「商机阶段变化」入同一时间轴）；

**`needResult` 规则（06 疑点 19 的结论）**

- `stage` 0→1、1→2、2→3：本接口直接推进一格，`needResult=false`。
- `stage=3` 时调用本接口：**不做任何变更**，返回 `code=0` 且 `data.needResult=true`、`stage` 仍为 3；客户端据此切到 `POST /deals/{id}/close`。
- 原因：库级约束 `ck_deal_result`（`stage <> 4 OR result IS NOT NULL`）要求「阶段 4 必有结果」。若本接口先把 stage 写成 4 再等客户端选结果，中间态会违反约束；把 3→4 收口到 033 一个端点、一次事务写 `stage=4 + result + closed_at`，约束不放宽、状态机不可绕过。
- 输单/赢单后能否回退：能，ADMIN 走 054，回退时 `result / lost_reason / closed_at` 一并清空。

**验收**：AC-DEAL-11 推进只能前进一格；AC-DEAL-12 到「签约」再推进时返回 needResult=true 且 stage 不变；AC-DEAL-13 推进写系统跟进；AC-DEAL-14 已结案商机推进返回 1001。

**依赖**：BE-API-033、DB-TBL-11/12。
