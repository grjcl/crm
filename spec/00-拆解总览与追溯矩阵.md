## 1. 拆解方法

### 1.1 五步法

1. **锁基线**：以 PRD 为准（★3），技术方案只取约束（★2），原型只取交互（★1），xlsx 只取编号（来源追溯）。
2. **对基线做交叉核对**：PRD §12.1 字段 vs §6–§11 需求 vs 原型字段 vs 54 接口，找出缺口（→ `06` 的 C 系列契约变更建议）。
3. **按切片建任务骨架**：用技术方案的 S0–S7 做**唯一**的先后顺序（重算接口归属，见 §5），在每个切片内按「表 → 后端服务 → 接口 → 前端页面/组件 → 测试」拆。
4. **把每个任务拆到「一次改动 + 一次可独立验证」**：凡是「做一个模块」级标题一律再拆（例：档案 360 拆成壳、概览、联系人、跟进、商机 5 个任务）。
5. **给每条判定建稳定 ID（AC-xxx）**：优先引用 PRD 已有验收项，缺的补写；全部汇总到附录，任务只引用 ID。

### 1.2 任务 ID 规则

| 前缀 | 含义 | 示例 |
|---|---|---|
| `DB-` | 数据层（迁移、建表、扩展、种子） | `DB-TBL-13` |
| `BE-API-` | 一个接口一个任务（编号严格对应 PRD 接口 #，共 001…054） | `BE-API-032` |
| `BE-` 其它 | 后端服务、中间件、领域逻辑、worker、推送、埋点 | `BE-DEDUP-001` |
| `FE-PAGE-` | 一个页面或一个页签 | `FE-PAGE-007` |
| `FE-COMP-` | 一个可复用组件/弹层 | `FE-COMP-001` |
| `FE-` 其它 | 工程骨架、通用能力、离线、推送、更新 | `FE-OFF-001` |
| `INFRA-` | 部署、CI、存储、资质、打包、备份 | `INFRA-009` |
| `TEST-` | 单测、端到端、演示数据 | `TEST-E2E-004` |

> 注意：`BE-API-014` 是「接口 #14」，不是第 14 个后端任务。所有 `BE-API-001`…`BE-API-054` 与 PRD §13.2 的编号**一一对应**，便于对着接口清单点检。

### 1.3 每个任务写什么

任务书 §4 的 11 个字段全部落位：标题 / 切片 / 端 / 需求来源 / 依赖 / 输入输出 / 规则校验 / 异常边界 / 验收标准 / 风险备注。字段级细节不重复写在 05，而是引用 `01`（表）、`02`（入参出参）、`03`（交互）、`04`（规则）——**同一件事只定义一处**。

### 2.4 为什么 S0 有 54 个任务

S0 除登录四个接口外，还承载**全部 16 张表的 DDL**（21 个数据任务，含视图与 pg_trgm）与**全部横向中间件**（鉴权 4 件、错误码、幂等、审计、脱敏、密码策略、统一响应、分页、OpenAPI 生成、CI 与部署 4 件）。这是刻意的：数据库与契约是所有切片的前置，放到 S0 才符合「按端点只归一个切片」的原则（见 §5）。若按技术方案原来的「表跟着功能走」，会出现 S2 建表、S3 改表、S4 再改表的返工。

## 5. 切片与接口归属（对 06 疑点 24 的结论）
