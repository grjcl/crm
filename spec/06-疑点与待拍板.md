# 06 · 疑点与待拍板

> 输入：任务书 §6 列出的 27 条 + 拆解过程中新发现的 21 条（B 系列）。
> 每条给：**现象 → 影响 → 建议（结论倾向）→ 谁拍板 → 是否阻塞开工**。
> 判定口径：**阻塞开工** = 不做决定就无法开工/无法验收，且无法用默认值绕开；**不阻塞** = 有可执行的默认值，先按默认做，事后可改。
> 结论分三类：**确认**（问题成立，按建议执行）、**修正**（原描述有误，给出正确口径）、**待拍板**（必须有人定，但已给推荐项）。

### 1.1 缺 `GET /users` 用户列表接口 —— 待拍板 · **阻塞**

**现象**：归属销售选择器、协作人多选、交接选人、线索分配、商机负责人都要「全员列表」；§13.2 的 54 个接口里没有 `GET /users`，`/meta/dicts` 也不含用户。

**影响**：清单 2.8（归属与协作人，必做）、3.8（合作交接）、5.3（分配线索）、5.5（商机负责人）都需要它。一期虽不做交接/分配的 UI，但**新建合作商的「协作人」与商机的「负责人」**在表单上就存在；没有候选列表只能手输 id。

**建议（结论倾向：新增）**：
- 新增 **C-09 `GET /users?enabled=true`**，返回 `[{id,name,dept,role}]`，权限 A（SALES 也需要看同事名字才能选协作人）。
- 这会打破「54 个接口」的冻结基线，所以**不擅自加**：已单列在 §3 契约变更建议，需 owner 按 tag 重新冻结（`v0.3-contract`）。
- 若**不新增**，降级方案：一期隐藏「协作人」与「负责人（他人）」控件（SALES 恒为本人），并在 04 `R-OUT` 登记；代价是 2.8 只交付一半，清单 2.8 的验收要改为「仅归属销售」。

**谁拍板**：owner（产品负责人）；技术侧只需在新旧 tag 间二选一。
**阻塞**：**是**。FE-COMP-009、BE-API-047/053 的可用性都取决于它。

### 1.6 §10 标题「10 项」与 §2.1「12 跟进记录 8 项」不一致 —— 修正

**现象**：任务书说 §10 标题写「10 项」，§2.1 写「8 项」。

**顺带核对**：任务书 §2 说「`是否一期=否` 的行（1.1 / 1.5 / 6.2 / 6.3）」——**核实正确**，xlsx 中正是这四行 H 列为「否」。

### 1.10 查重算法未定 —— 确认（已定）

**结论**：
- 算法：PostgreSQL `pg_trgm` 的 `similarity()`（需 `CREATE EXTENSION pg_trgm` + GIN 索引）。
- 归一化：去中英文括号及内容 → 去所有空白 → 全角转半角 → 英文字母小写（04 `R-DEDUP-01`）。
- `lead` 与 `org` **同一套**归一化与阈值 `> 0.9`。
**理由**：不引第三方模糊匹配库，PG 原生即可，性能对 <1GB 数据无压力。
**拍板**：不需要（技术选型，已写进 01/04）。

### 1.11 `lead_pool.fingerprint` 唯一与空电话 —— 确认

**结论**：指纹 = `sha256(归一化名称 + '|' + (归一化电话或空串))`。
- 电话缺失时用空串 → **仅按名称去重**，同一名称的第二条采集直接跳过（记 `skipped`）。
- 丢弃的条目**仍占指纹**（唯一索引不分状态），即「丢掉的不会被重新采进来」。若业务希望丢弃后可重采，改部分唯一索引 `WHERE status <> '已丢弃'`（01 §2.10 已写改法）。
**拍板**：需产品确认「丢弃后是否允许重采」；**不阻塞**（默认不重采）。

## 2. 拆解中新发现（B 系列）

### B1 · `org.collaborator_ids` 没有承载字段 —— 待拍板（不阻塞，但有默认）

**现象**：PRD §6.1 的「协作人 多选用户」是必做字段，但 §12.1 的 `org` 字段清单里没有协作人；16 张表也没有关联表。

**拍板**：owner 确认字段级变更；**不阻塞**（默认加列）。

### B2 · `channel` 删除时 `lead_pool.channel_id` 的处理 —— 确认
FK 用 `ON DELETE SET NULL`，删除渠道后池内数据保留且 `channel=null`（PRD §11.2「已采集的池内数据保留」）。已写进 01 §2.14 / 02 §BE-API-037。

### B3 · `follow.deal_id` 与 `deal` 建表顺序 —— 确认
`follow` 在 `deal` 之前建（PRD 表序），FK 需在 deal 建完后 `ALTER TABLE` 添加。01 §1 已给出两种落地方式并推荐 A。

### B4 · `GET /partners` 缺 `type` 参数 —— 待拍板（不阻塞）
PRD §13.2 只列 `tag/city/level/status/q/owner/page/size`；清单 3.2 说合作类型「用于筛选统计」。建议补 `type`（02 §BE-API-005 已加）。**默认加**，因为不加则清单 3.2 的「用于筛选」落空。

### B5 · refresh token 是否轮换 —— 确认
一期**不轮换**（同一 refresh 30 天内可多次换 access），只做黑名单。理由：轮换需处理「旧 refresh 被重放」的并发，10 人内网场景收益低。

### B7 · 合作商主档是否需要乐观锁 —— 确认
一期**不加 `version`**，后写覆盖 + 审计留痕。理由：主档字段多、编辑频率低，加 version 会让每次编辑都要先拉详情；如出现真实覆盖事故再加。

### B8 · 回收站 30 天后的清理 —— 确认
**不自动物理删除**（避免误删不可恢复）。运维按季度执行清理脚本，先导出再删。若 owner 要求自动，加定时任务（属运维，不影响契约）。

### B9 · 图片 ≤300KB 的校验责任 —— 确认
服务端只校验 ≤10MB；≤300KB 由客户端压缩保证。理由：服务端再压会二次损失，且原型/PRD 都把压缩写在客户端流程里。若服务端要硬校验 300KB，会拒掉合法的原图直传路径（PDF 不压缩）。
