# Transactional idempotency infrastructure

This is an explicit synchronous component, **not HTTP interception**. `@Idempotent` is a marker only: no current endpoint enforces it or is protected by it. Integration and the HTTP error contract remain future work. R-LOCK-06 requires a key for seven operations: create partner, add follow-up, save plan, claim, close, register attachment, and advance. BE-SEC-006 specifies that a POST without a key proceeds non-idempotently except for the mandatory whitelist; the adapter must bypass this service for such requests. This conflicts with workspace guidance that all POST writes carry a key. The general API rules say PUT/DELETE do not require keys, but R-LOCK-06 requires one for saving a plan (a PUT); reconcile that conflict and response mappings before HTTP integration. No OpenAPI contract file is currently present to resolve the discrepancies. Authentication behavior is unchanged.

After authentication and authorization, validate that exactly one `Idempotency-Key` header was supplied. Call `execute(userId, key, method, target, body, operation)` **outside any transaction**. The method starts and commits its own READ COMMITTED transaction; calling inside another transaction is rejected so a response cannot escape before commit. The target must be the stable HTTP path plus raw query, and body the exact request bytes. The operation must perform all database writes through the same PostgreSQL datasource and transaction manager and serialize the complete response inside the callback. Do not catch a failure and return a success response after partial writes; throw to roll back. A returned response, including a deliberately returned error response, is committed and replayed. Only status, content type and body bytes are retained; endpoints requiring other response headers need an extended contract. Do not use for streaming, async or multipart operations. This component does not protect external side effects, independent transactions, or other databases; an outbox or other separate protocol is required for those.

The scope is user ID + method and path (without query) + key; method/path/key are hashed and request method, full target including query, and exact body are fingerprinted. Different query or body with the same unexpired scope is `CONFLICT`; another user, method or path is independent. Keys must be nonempty visible ASCII, at most 200 characters. The HTTP adapter must map `INVALID_KEY`, `CONFLICT`, and `STORE_UNAVAILABLE` to agreed API responses. Concurrent requests block on PostgreSQL uniqueness/row locks until the first commits or rolls back: on commit they replay or conflict; on rollback a contender executes. `IN_PROGRESS` is reserved for compatibility, not normally emitted. Database lock timeouts and outages fail closed; commit outcome may be uncertain, so retry the same key. No HTTP response should be emitted until `execute` returns successfully. Stored responses expire 24 hours after completion, at which point a locked row may be reused, including with a different request; retry after expiry can create another write. Expired rows are reused on demand and currently have no cleanup job. No keys or payloads are logged here.

The component uses PostgreSQL only, not Redis. Existing application Redis configuration does not set a database and therefore defaults to 0, conflicting with the database 9 requirement; this change neither uses nor reconfigures Redis, so that existing-service discrepancy must be addressed separately. PostgreSQL idempotency records and business writes commit or roll back together, but deployment, endpoint wiring, HTTP semantics, and production cleanup/retention policy remain to be addressed before claiming endpoint-level AC-INFRA-10 or AC-FOLLOW-07.
